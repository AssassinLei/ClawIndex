# ClawIndex 一键更新方案

日期：2026-10-12。状态：设计方案，尚未创建Actions工作流、Docker构建配置或部署脚本，未连接云服务器、推送代码或发布镜像。

## 目标与已知条件

用户在Windows本地开发，目前逐个上传文件到Linux云服务器并重启。已选择Docker Compose。当前仓库remote为`https://github.com/AssassinLei/ClawIndex.git`；仓库公开性、服务器架构、网络及访问凭据未核实。新版容器运行配置尚待实施，先完成容器化和Linux验收，再接发布自动化。

一次更新应该取得一套完整、可识别、已验证的程序版本，保留服务器的数据和密钥，确认页面与worker运行正常，失败能明确恢复。普通代码更新与数据库结构迁移分开处理。提交开发代码并不意味着立刻更换生产版本。

## 选择

| 方案 | 更新操作 | 优点 | 适用条件与代价 |
| --- | --- | --- | --- |
| Git版本 + 服务器更新命令 | 推送代码后，服务器执行一次更新命令 | 实现较小，完整更新代码 | 服务器还需构建/安装依赖；需按指定提交使用发布目录，不能仅在运行目录直接pull |
| GitHub Actions构建镜像 + 服务器更新命令 | 推送发布版本，服务器拉取并更新 | 在CI统一构建，服务器无需安装Python依赖 | 需容器化、镜像仓库访问及一次性部署配置 |
| GitHub Actions构建镜像 + 点击部署 | 推送发布版本后，在Actions选择版本、点Run workflow | 日常无需SSH登录或上传文件，可查看部署结果 | Actions必须能通过受限部署通道访问服务器 |
| 本地打包镜像/发布包 + 一键传输 | 本地命令一次完成打包传输与部署 | 服务器无法稳定访问GitHub/镜像仓库时可用 | 本地构建需匹配Linux架构与依赖，并承担打包测试 |

推荐第二种作为基础，第三种作为最终操作入口。两者调用同一服务器部署程序，避免形成两套更新逻辑。若服务器在国内，先实际测试GitHub、GHCR和基础镜像下载；访问不可靠时改用云厂商镜像仓库，发布过程保持不变。

## 推荐流程

```mermaid
flowchart LR
    A[本地开发与提交] --> B[GitHub Linux测试]
    B --> C[构建与测试镜像]
    C --> D[发布固定版本及摘要]
    D --> E[选择已验证版本并点击部署]
    E --> F[服务器部署命令]
    F --> G[校验并预拉取]
    G --> H[更新web和worker]
    H --> I[检查页面与任务运行]
    I --> J[记录成功或恢复旧版]
```

GitHub Actions支持构建并推送Docker镜像到GitHub Container Registry（GHCR），也支持`workflow_dispatch`手动触发工作流。参考[官方镜像发布流程](https://docs.github.com/en/actions/tutorials/publish-packages/publish-docker-images)与[手动运行工作流](https://docs.github.com/en/actions/how-tos/manage-workflow-runs/manually-run-a-workflow)。手动触发工作流需先存在于默认分支。

每个发布版本绑定源码提交、镜像digest、匹配的Compose文件和版本清单。清单包含应用版本、支持的schema范围、是否需迁移、Python/SQLite版本、构建平台及测试结果。部署使用`image@sha256:...`，不能以可变`latest`作为回滚依据。Compose配置随匹配发布包取得，无需日常手工上传多个文件；新版本若需额外密钥或配置，预检应明确阻止并说明一次性的补充步骤。

## 服务器部署程序的职责

以下为拟实现步骤，当前没有可运行的更新命令：

1. 对整个部署加锁，记录当前版本和目标版本，防止点击两次或两个发布并发执行。
2. 获取匹配发布清单/配置/镜像，校验来源和摘要，检查架构、磁盘、配置、挂载目录、schema兼容性与SQLite修复版本。失败时保持当前服务运行。
3. 在停止当前服务之前拉取全部目标镜像。网络失败不能让正在运行的系统被提前关闭。
4. 停止web和worker，阻止新写入，取得一致性备份并记录恢复清单。涉及schema迁移的版本进入明确的迁移流程，默认普通更新不隐式改表。
5. 使用同一目标镜像和匹配Compose配置启动两项服务。数据目录与生产配置独立持久保存；不执行删除数据卷的操作。单机SQLite默认接受一次短暂维护窗口，不承诺零停机。
6. 有界等待：页面HTTP、数据库就绪、worker心跳及处理循环检查。部署诊断不得请求真实付费行情、发送Webhook或修改投资信号；可使用单独的内部诊断任务确认队列被取走。仅HTTP 200或容器running不足以判定成功。
7. 成功后记录版本、摘要、时间及诊断结果；保留上一版本镜像和配置。普通兼容更新失败时恢复旧镜像/配置并再次检查；若schema已变化，必须按迁移方案恢复配套备份，并说明可能丢失维护窗口后新增记录，不能盲目只回退镜像。

Compose在镜像或配置变化时可重建服务并保留挂载数据，参考[Compose up官方说明](https://docs.docker.com/reference/cli/docker/compose/up/)。拉取和重启是部署步骤的一部分，不包含本方案要求的备份、兼容性检查和失败恢复。

## 一次性配置与日常操作

一次性完成Docker/Compose安装、服务器数据目录与备份目录、生产配置、受限网页访问、镜像拉取认证及部署通道。Actions上传镜像使用适当权限的GITHUB_TOKEN；服务器拉取私有GHCR镜像使用仅需读包权限的凭据，不能复用短时CI token。参考[GHCR认证说明](https://docs.github.com/en/packages/working-with-a-github-packages-registry/working-with-the-container-registry)。Tushare、LLM密钥和生产数据库始终留在服务器，构建上下文也需排除，不上传到GitHub或镜像。

自动部署通道优先使用SSH调用固定部署入口，验证服务器host key，凭据放GitHub Secrets，不放源码。部署权限按实际能力限制；可调用Docker本身即有很高的宿主权限，不能声称普通Docker组账号完全受限。开发/PR测试不接生产部署凭据。生产只接受明确选择且已通过测试的发布版本，工作流和服务器部署锁共同约束并发。

若Actions无法连接服务器，保留服务器执行一次更新命令的入口；不为方便而将管理接口暴露到无身份校验的账号名网页。用户电脑能SSH时，也可提供本地PowerShell薄包装器调用同一服务器入口。无需先引入Kubernetes、生产机器自托管runner或持续轮询latest自动换版本。

日常操作目标是：本地开发 → 推送版本 → 等待测试与构建通过 → GitHub Actions选择版本并点Run workflow → 查看成功/失败及当前生产版本。提交和部署是两个独立动作，首次配置成本只发生一次。
