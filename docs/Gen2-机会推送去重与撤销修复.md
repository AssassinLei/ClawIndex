# 机会Webhook：只推送当前机会

## 核实到的问题

2026-10-23用户反馈机会卡片显示“机会已撤销”，并出现同一指数重复通知。代码与隔离测试证实：

1. 旧规则本来允许发送撤销。撤销分支没有像新增机会一样检查个人隐藏列表，因此“暂不关注”后仍可能收到撤销卡片。
2. 撤销队列的身份包含每次扫描报告编号；上一条撤销尚未成功发送时，行情修订或重新扫描又会创建新的撤销任务。Cron等待期间可以积累多条，到发送时间连续发送。
3. 投递时缺少跨旧队列行的成功去重与同指数发送中互斥，旧队列中不同编号的重复机会也可能各发一次。

上述路径已经用合成数据复现。当前本地库没有云端机会发送记录，无法把截图中的每条消息对应到某个云端队列或渠道；不能仅凭截图排除多个账号或渠道向同一群发送的情况。

## 用户确认后的规则

Webhook只推送**发送时仍存在于“发现机会”当前个人候选中的机会**，不推送“机会已撤销”。

- 机会提醒默认关闭，各账号、各Webhook独立选择“当前观察机会与条件满足”或“仅当前条件满足”。保存的`ALL`、`READY`、`OFF`配置值兼容，无需重新配置。
- 发送前重新核对最新完整扫描、规则版本、已发布行情日期、候选是否仍入选、个人隐藏偏好、渠道总开关和Cron窗口。
- “暂不关注”的代码不在个人候选中，不能发送。加入监控后默认隐藏该指数的机会推荐；如果关闭“隐藏已关注的指数”，仍可按显示偏好接收。
- “停止监控”负责停止个人巡检，不等于永久排除共享机会扫描；不希望之后再被推荐的代码，应在“发现机会”选择“暂不关注”。本次不改变这两类操作的区分。
- 条件失效、被隐藏、退出当前候选、数据未就绪或过期时不发送旧机会。撤销和失败案例继续留在系统记录与后续跟踪中。
- 持续不变的候选不每天重播。本次也没有改成每日全量摘要。

## 去重与升级处理

新队列按“账号＋渠道＋指数代码＋行情日期＋机会阶段”确定身份，扫描报告编号不再制造新的发送身份。同一行情日已成功发送的阶段不再发送；先通知观察、后来真正升级为条件满足时，最多补发一次。若观察还在等Cron、就已升级，只保留当前条件满足的通知。下一行情日真正重新出现的机会仍可正常通知。

投递前还会识别旧版本不同编号的重复队列，以及请求过程中关闭渠道但发送实际成功的审计记录。队列取消不能抹掉实际成功记录，避免重新开启后重发。同一指数、同一渠道、同一行情日有请求仍持有有效发送租约时，其他重复行等待，不阻塞其他指数与渠道。

升级后，后台第一次机会投递维护就会将旧`WITHDRAWN`待发送、重试和发送中队列取消，不需要等待Cron，也不需要用户清库。历史已发送记录、真实审计、数据、持仓、Webhook地址和Cron配置保留。已经进入外部HTTP请求的消息无法撤回。

失败仍沿用最多3次尝试及退避；外部Webhook在网络超时下没有事务性确认，因此不把本次业务去重表述为任意断网情形下的绝对恰好一次投递。

## 测试与部署

回归覆盖：只留系统撤销记录而不入推送队列、旧撤销任务在Cron前取消、旧重复行去重、Cron等待期间反复扫描不积累重复、隐藏后的旧任务不发送、观察升级前后去重、发送租约互斥、成功审计与关闭竞态、新行情日正常提醒，以及原有渠道隔离、Cron、父级行业信息和有限重试。所有发送均使用假的sender，没有向真实Webhook发送消息，也没有修改生产库。
